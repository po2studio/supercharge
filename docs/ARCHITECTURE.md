# Architecture

## Components

- **Skills:** `skills/<name>/SKILL.md`, Markdown with `name` (matching the folder) and `description` frontmatter. Each skill guides an omp or Claude Code session or subagent; none contains code. A skill folder may hold more files: `supercharge` ships `issue-template.md`, the default issue format, which a project replaces with its own `docs/issue-template.md`; `brain` ships `brain.json`, the pins for its binary, and `brain-ci.yml`, the workflow it writes into a GitHub brain repo.
  - `living-docs` writes `AGENTS.md` and `docs/`; `adr` writes `docs/adr/`; `supercharge` is the entry point: it runs `living-docs` to set a project up, writes `docs/features/` and GitHub issues, and hands a feature to `drive-feature` and builds a ticket with `build-slice` in a fresh builder subagent.
  - `drive-feature` runs `build-slice` per slice in fresh subagents (omp's `task`; `sonnet` in Claude Code), ticks each slice on the feature issue as it merges, then runs `living-docs` at the finish, in its own session, never a subagent. `build-slice` writes the code, tests and docs, and opens the PR.
  - `brain` is optional: it answers questions from the project's own docs and the folders its `AGENTS.md` lists, with the `brain` binary, set up on first use after the human says `go`. With an `update: true` source it also searches for what is already decided before `supercharge` asks, records the answers as `decisions/` files after `go`, writes a `notes/` file on demand when an answer had to combine several files, lints the stale notes, and runs the ship step after every merge into `main`, in a builder subagent started by the skill that merged; those skills carry one line each pointing at it. The ship step also covers every commit since the project's last reconciled one (`projects/<project>.yaml`), and `build-slice` checks a PR's paths against the decisions and notes that `touch` them. `/brain refresh` lints every note. When the source is a GitHub repo, the skill adds the CI workflow that runs `brain check`. The other skills work without it.
  - Skills share no code. Apart from one skill starting another, they coordinate only through those files, the config block in `AGENTS.md`, and GitHub issues and PRs.
- **`runs/`:** write-ups of real runs, the evidence behind the README's model table.
- **`scripts/check.py`:** checks each skill's frontmatter (a description's first sentence is at most 57 characters, since the skills CLI cuts its hint there, and the whole at most 1024), `skills/brain/brain.json`, and every relative link in the repo's Markdown. CI (`.github/workflows/check.yml`) runs it on PRs and on pushes to `main`.
- **`brain/`:** the Rust crate behind the `brain` skill ([ADR 0002](adr/0002-local-embeddings-one-sqlite-index.md), [ADR 0003](adr/0003-the-brain-is-a-folder.md), [ADR 0004](adr/0004-brain-sources-per-project.md)). A command run inside a project resolves its sources itself (`src/sources.rs`): the project, found as the nearest folder with a `.git` (else an `AGENTS.md`) above the current directory, contributes its docs folder (the `docs` key of the `## Supercharge` block in its `AGENTS.md`), `README.md` and `AGENTS.md`, read in place; the `brain:` list of that block adds outside folders; `--repo` and `--source` override both. At most one source sets `update: true`, and two are an error naming both. `index` walks each source and embeds only files whose content hash changed, and only refreshes a date that moved. What a file is comes from its extension (`src/convert/`): Markdown and text as they are; HTML, PDF text layers, Word, Excel, PowerPoint, OpenDocument, RTF, email and CSV converted to Markdown-ish text (pipe tables, `#` headings), with the document's own title and date; JSON, YAML and code as text without headings; an unknown extension as text when it is, else unconverted. A file with no text to give (a scan, an image, audio, video, an archive, an encrypted or corrupt file) is stored as unconverted with its reason, by content hash so it is not tried again, and listed by `stats`; it is never an error. Every converter that parses a structured format runs in a child process (`brain convert-child`, a hidden command) limited to 3 GiB of memory and 120 s, so a hostile or damaged file is reported as unconverted instead of taking the indexer down. Conversions of containers (PDF, Office, OpenDocument, email) are cached in `convert/` beside the index file, by content hash and format, and removed with the file. Chunker v2: headings, paragraphs, lines, sentences, words, then a hard cut; about 400 tokens, 10% overlap; a table is cut into row groups that each repeat its header, a transcript by speaker turn, a fenced code block is never cut at a blank line, and code has no headings; each chunk's context header is cut to 96 tokens so header and text fit the model's 512. After every run `src/dedup.rs` groups exact copies (same content hash) and near-copies (SimHash over distinct word pairs, at most 7 bits apart) and marks all but the newest of each group as hidden; `search` skips hidden files and lists them as the newest's `versions`. Text over 1 MiB (also converted text) and files it cannot read are listed as left out, never silently dropped; `search` runs BM25 over SQLite FTS5 (`--terms`) and cosine over the int8 vectors (`--about`) in each source's index, merges each mode's results across sources by score, fuses the two by rank (RRF), one hit per file, each naming its source. A decision's frontmatter (`kind`, `project`, `status`, `supersedes`, `superseded-by`) and a project ADR's status line (`superseded by`, `amended by`) are indexed with the file (`src/doc.rs`), and `src/decisions.rs` settles every file's status across its source after each index run, so a decision that an accepted one `supersedes` is hidden even if its own status was never updated. `search` applies `--kind`, `--project`, `--since` and `--status` in SQL before ranking, leaves superseded entries out unless `--all` (or `--status superseded`), moves an accepted decision or ADR up one place, and brings an amended ADR's amendments with it; `stats` and `eval` report on it. `multilingual-e5-small` (int8) is compiled in and run with ONNX Runtime. There is one SQLite file per source under `~/.cache/supercharge/index/<source-hash>/` (the project's docs are one source; `SUPERCHARGE_CACHE_DIR` moves the cache), rebuilt when the model ID, binary version, chunker version or table layout changes, and shared by every project that lists the same folder. `index`, `search` and `stats` never write into a project or a source; `init` is the one command that does, creating `BRAIN.md`, `decisions/`, `notes/` and `projects/` in the `update: true` source if they're missing, and the skill runs it. `brain eval` indexes the project in `brain/eval/project/` and the corpus `brain/eval/corpus/` as two sources, asks `brain/eval/questions/*.yaml` and compares recall@5, MRR, search latency and indexing speed with `brain/eval/baseline.json`. Its CI is `.github/workflows/brain-ci.yml`, which runs only when `brain/` changes: format, clippy, tests, eval.
- **Notes (`brain/src/notes.rs`):** a file in `notes/` of any source is a note. Its frontmatter (`summary`, `aliases`, `questions`, `sources: [{path, hash}]`, `verified`) is indexed with it: the summary, questions and aliases are part of its text, so a question it answers finds it, and `verified` is its date. A source's `path` is `<source>:<path>`, the source as a hit labels it (`project` for the project's docs) and none for a file of the note's own source; its `hash` is the file's sha256, the content hash the index keeps. Staleness is read, never stored, because the sources a note names live in other indexes and an index is shared by every project that lists its source: after `index`, and in every `search` and `stats`, a note is stale when a source's hash differs, the file is gone, or it names no source (a note about another project's docs is not judged from this one). `search` flags `stale` and applies the trust order (accepted decisions, fresh notes, raw files, stale notes): a fresh note takes the one-place lift decisions have, below a decision it ties with, and a stale one goes after every raw file and doesn't count towards the top `k`. `stats` lists the stale notes with each source's current hash, the notes with no source left, and the notes made from the same files as a newer one, or saying nearly what it says.
- **Shared index (`brain/src/shared.rs`, `bench.rs`):** a brain repo's CI (the `index` job of `skills/brain/brain-ci.yml`, on the default branch) runs `brain pack`: it indexes the repo's own files, starting from the index it last published, and writes the SQLite file gzipped as `brain-index_<model>_<binary version>_<commit>.sqlite.gz.NNN`, parts of at most 1.9 GB because a release asset may not pass 2 GiB. The workflow uploads them to the repo's release `brain-index` and keeps the newest two indexes. It never holds a project's docs, which are not part of a brain repo. `brain index` of an outside source that is a brain repo (its `origin` is on github.com and it has `.github/workflows/brain.yml`) with no usable local index lists that release with `gh`, takes the newest index of this model and binary version whose parts are all there, unpacks it, checks it against the meta it records (model, binary version, chunker, schema), records where it came from in its `meta` (`stats` shows it), and then indexes as usual, so only files that differ are embedded; it says why and builds locally on no match, no `gh` or no network. `pack --budget <minutes>` stops indexing at the next group of chunks and reports `incomplete`, and the workflow starts itself again: a brain too big for one job is built over several. Release assets rather than Actions artifacts: artifacts expire (90 days by default) and count against the plan's artifact storage (500 MB on a free plan), assets do neither, and a fetch by `gh release download` needs no run id; measured speeds were alike in the runner, and from a laptop an asset came down in 14 s against 37 s for the artifact ([the run](../runs/2026-11-22-brain-shared-index.md)). `brain bench` fills an index with synthetic chunks (random vectors, prose-like text), times searches in process and as the command line runs them, and times the real model indexing real-looking documents; `--write-brain` writes a synthetic brain repo, and `brain/scripts/scale.sh` runs both scale measurements with a released binary.
- **Checks (`brain/src/check.rs`):** `brain check` reads the files agents own in the brain (the `update: true` source, or the folder you are in when it holds a `BRAIN.md`, which is the brain repo's CI) and writes nothing, loads no model and needs no index. It fails, naming file and reason, on invalid decision or note frontmatter (required fields and values, `touches` without `project`, a `supersedes` or `superseded-by` naming no decision, a note source without a sha256), a broken relative link in `BRAIN.md`, `decisions/` or `notes/`, and an accepted decision whose body, or any field but `status` and `superseded-by`, differs from its first accepted version in git history (a brain that isn't a git repo skips this). A stale note, judged against the brain's own files and, run in a project, that project's and the listed sources', and an entry of the project whose `touches` globs match no file in it, only warn. `check --changed <paths | A..B>` instead lists the entries of the project whose `touches` match, `A..B` taking every path any commit in the range touched; `--json` gives either for tools. The workflow `skills/brain/brain-ci.yml`, filled in by the skill with the pinned binary's tag and sha256 and written to the brain repo as `.github/workflows/brain.yml`, runs `brain check` on every push and pull request and keeps one `brain-stale` issue open while notes are stale.

## Runtime

The skills run in omp and in Claude Code. In omp the agent picks the agent, and omp's model roles set its model. They use `task` subagents (builders, on the `task` model role), the `reviewer` agent (on `slow`), `sonic` (on `smol`, for the `brain` skill's searches: it has a shell, which `scout` lacks), `browser`, the `github` tool, isolated worktrees for parallel slices, and `gh` to create issues, which the `github` tool can't do. In Claude Code they use fresh subagents, never forks (builders on `sonnet`, the reviewer on a different Claude model), `isolation: "worktree"` for parallel slices outside Orca (in Orca, both runtimes use worktrees made with `orca worktree create` as children of the session's, so Orca nests and removes them), a headless browser through the project's test tooling, and `gh`; Claude Code reads `AGENTS.md` itself, or through a `CLAUDE.md` that imports it. Each slice's branch starts from the PR's target branch, wherever its worktree started. Only `drive-feature` edits a one-issue feature's issue, to tick a slice after it merges, so two writers never overwrite each other's tick. If a feature a skill names isn't available, it uses an equivalent or stops and says so; no equivalent replaces a fresh subagent or a reviewer on a different model. The `brain` skill searches in a `sonic` agent (omp, on `smol`) or a fresh subagent on `haiku` (Claude Code), so snippets stay out of the session; the same skill runs the `brain` binary, the only code the bundle executes.

## Distribution

The skills CLI installs from this GitHub repo: `npx skills add po2studio/supercharge -g -a pi` (omp) or `-a claude-code` (Claude Code) copies each `skills/<name>` folder into `~/.agents/skills` or `~/.claude/skills`, and `npx skills update -g` refreshes them. It copies only `skills/<name>/`, so the `brain/` source never reaches a user's machine, and skipping the `brain` skill at install changes nothing else. The skills have no build step.

The binary is released from this repo ([ADR 0001](adr/0001-one-binary-in-the-bundle.md)). A tag `brain-vX.Y.Z` runs `.github/workflows/brain-release.yml`: it builds linux x64 and arm64, macOS arm64 and x64 on GitHub-hosted runners, smoke-tests each binary alone with an empty environment, and publishes a GitHub pre-release with the four binaries and their sha256. `skills/brain/brain.json` pins the version, and per platform the URL, size and sha256; the `brain` skill downloads with `gh release download` after the human says `go`, verifies the checksum, and caches the binary in `~/.cache/supercharge/brain/<version>/`. Linux binaries need glibc 2.34 or newer and no C++ runtime. ONNX Runtime 1.22 is linked statically from pyke's prebuilt libraries on all four platforms (pyke publishes none for macOS x64 after 1.22, which is why the version is pinned).

## External services

- **GitHub:** issues, labels, PRs, Actions, and releases (the binary's, and a brain repo's `brain-index` release). A feature is one issue whose checklist is the progress record, outside the codebase and the same for every agent; only features planned with sub-issues have sub-issues. No fake: without a GitHub remote, the skills use local branches and the checks in `AGENTS.md` instead, and the ticks stay in the feature doc.
- **Model providers,** through omp or Claude Code.

Everything but the `brain` binary is skill text, with no code to run. The binary works offline: the embedding model is compiled in and the I/O is the sources it reads and the index under `~/.cache/supercharge/`, so its unit tests and `brain eval` need no fakes. The one network use is `brain index` of an outside source that is a GitHub brain repo, which asks GitHub through `gh` for the index its CI published and builds locally when there is none or `gh` fails; `brain/tests/shared.rs` stands in for `gh` with a script that serves a release from a folder. The one embedding interface (`Embedder`) has a hashed bag-of-words fake for unit tests.
