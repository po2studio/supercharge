# Architecture

## Components

- **Skills:** `skills/<name>/SKILL.md`, Markdown with `name` (matching the folder) and `description` frontmatter. Each skill guides an omp or Claude Code session or subagent; none contains code. A skill folder may hold more files: `supercharge` ships `issue-template.md`, the default issue format, which a project replaces with its own `docs/issue-template.md`; `brain` ships `brain.json`, the pins for its binary.
  - `living-docs` writes `AGENTS.md` and `docs/`; `adr` writes `docs/adr/`; `supercharge` is the entry point: it runs `living-docs` to set a project up, writes `docs/features/` and GitHub issues, and hands a feature to `drive-feature` and builds a ticket with `build-slice` in a fresh builder subagent.
  - `drive-feature` runs `build-slice` per slice in fresh subagents (omp's `task`; `sonnet` in Claude Code), ticks each slice on the feature issue as it merges, then runs `living-docs` at the finish, in its own session, never a subagent. `build-slice` writes the code, tests and docs, and opens the PR.
  - `brain` is optional: it answers questions from a folder of documents with the `brain` binary, set up on first use after the human says `go`. The other skills work without it.
  - Skills share no code. Apart from one skill starting another, they coordinate only through those files, the config block in `AGENTS.md`, and GitHub issues and PRs.
- **`runs/`:** write-ups of real runs, the evidence behind the README's model table.
- **`scripts/check.py`:** checks each skill's frontmatter (a description's first sentence is at most 57 characters, since the skills CLI cuts its hint there, and the whole at most 1024), `skills/brain/brain.json`, and every relative link in the repo's Markdown. CI (`.github/workflows/check.yml`) runs it on PRs and on pushes to `main`.
- **`brain/`:** the Rust crate behind the `brain` skill ([ADR 0002](adr/0002-local-embeddings-one-sqlite-index.md), [ADR 0003](adr/0003-the-brain-is-a-folder.md)). `index` walks the brain folder and embeds only files whose content hash changed (chunker v1: headings, paragraphs, lines, sentences, words, then a hard cut; about 400 tokens, 10% overlap); `search` fuses BM25 over SQLite FTS5 (`--terms`) with cosine over the int8 vectors (`--about`) by rank (RRF), one hit per file; `stats` and `eval` report on it. `multilingual-e5-small` (int8) is compiled in and run with ONNX Runtime. The index is one SQLite file per brain under `~/.cache/supercharge/index/<root-hash>/` (`SUPERCHARGE_CACHE_DIR` moves the cache), rebuilt when the model ID, binary version or chunker version changes; nothing is ever written into the brain. `brain eval` indexes `brain/eval/corpus/`, asks `brain/eval/questions/*.yaml` and compares recall@5, MRR, search latency and indexing speed with `brain/eval/baseline.json`. Its CI is `.github/workflows/brain-ci.yml`, which runs only when `brain/` changes: format, clippy, tests, eval.

## Runtime

The skills run in omp and in Claude Code. In omp the agent picks the agent, and omp's model roles set its model. They use `task` subagents (builders, on the `task` model role), the `reviewer` agent (on `slow`), `scout` (on `smol`), `browser`, the `github` tool, isolated worktrees for parallel slices, and `gh` to create issues, which the `github` tool can't do. In Claude Code they use fresh subagents, never forks (builders on `sonnet`, the reviewer on a different Claude model), `isolation: "worktree"` for parallel slices outside Orca (in Orca, both runtimes use worktrees made with `orca worktree create` as children of the session's, so Orca nests and removes them), a headless browser through the project's test tooling, and `gh`; Claude Code reads `AGENTS.md` itself, or through a `CLAUDE.md` that imports it. Each slice's branch starts from the PR's target branch, wherever its worktree started. Only `drive-feature` edits a one-issue feature's issue, to tick a slice after it merges, so two writers never overwrite each other's tick. If a feature a skill names isn't available, it uses an equivalent or stops and says so; no equivalent replaces a fresh subagent or a reviewer on a different model. The `brain` skill searches in a `scout` (omp, on `smol`) or a fresh subagent on `haiku` (Claude Code), so snippets stay out of the session; the same skill runs the `brain` binary, the only code the bundle executes.

## Distribution

The skills CLI installs from this GitHub repo: `npx skills add po2studio/supercharge -g -a pi` (omp) or `-a claude-code` (Claude Code) copies each `skills/<name>` folder into `~/.agents/skills` or `~/.claude/skills`, and `npx skills update -g` refreshes them. It copies only `skills/<name>/`, so the `brain/` source never reaches a user's machine, and skipping the `brain` skill at install changes nothing else. The skills have no build step.

The binary is released from this repo ([ADR 0001](adr/0001-one-binary-in-the-bundle.md)). A tag `brain-vX.Y.Z` runs `.github/workflows/brain-release.yml`: it builds linux x64 and arm64, macOS arm64 and x64 on GitHub-hosted runners, smoke-tests each binary alone with an empty environment, and publishes a GitHub pre-release with the four binaries and their sha256. `skills/brain/brain.json` pins the version, and per platform the URL, size and sha256; the `brain` skill downloads with `gh release download` after the human says `go`, verifies the checksum, and caches the binary in `~/.cache/supercharge/brain/<version>/`. Linux binaries need glibc 2.34 or newer and no C++ runtime. ONNX Runtime is linked statically from pyke's prebuilt libraries; pyke publishes none for macOS x64, so that platform builds ONNX Runtime from source with pyke's `ort-artifacts` tool, once, cached by version.

## External services

- **GitHub:** issues, labels, PRs, Actions. A feature is one issue whose checklist is the progress record, outside the codebase and the same for every agent; only features planned with sub-issues have sub-issues. No fake: without a GitHub remote, the skills use local branches and the checks in `AGENTS.md` instead, and the ticks stay in the feature doc.
- **Model providers,** through omp or Claude Code.

Everything but the `brain` binary is skill text, with no code to run. The binary runs offline: the embedding model is compiled in and the only I/O is the brain folder and the index under `~/.cache/supercharge/`, so its tests and `brain eval` need no fakes. The one embedding interface (`Embedder`) has a hashed bag-of-words fake for unit tests.
